# Maintainer notes: `audiences`

Evidence and history behind the rules in `CLAUDE.md`: measurements, test rounds, dated findings. Not loaded into sessions. Read the part you need before changing a rule; add new findings here, never to `CLAUDE.md`.

## Files

- `plugin/skills/audiences/SKILL.md` — the targeting skill. Self-contained, no references. Owns the segment/audience model, the three sources a field name may come from, the ambiguous-attribute table (country source, app version current vs on install, strict SemVer, unset attributes, language codes, AND vs OR), the insert-before-default rule, and the audience entry shape.

## Conventions and findings: `audiences`

- **Ground truth is the CLI source and the docs, in two halves.** Commands and flags: `src/commands/segments/*.ts` and `src/lib/asa-flags.ts` (`parseSegmentFilter`) in `adaptyteam/adapty-cli`; `segments create`/`update` arrived with adapty-cli#48 (`feat/segments-write`), after 0.9.3. Attribute meaning: https://adapty.io/docs/segments. Neither lists the server's `field_name` vocabulary, which is why the skill confirms only the names the CLI's own README and tests use (`ip_country`, `install_date`, `age`, `total_revenue_usd`, `campaign`, `ad_group`, `creative`) and routes every other name through an existing segment's `filters[]`. Don't extend that list from memory; extend it from a `segments get --json` you ran.
- **Baseline (2026-10-12), two scenarios, no skill.** A Germany/Austria paywall on a placement with a VIP audience, under "go ahead, don't check back"; and an app-version-and-never-paid flow audience plus a custom attribute. Failures: the new audience was put at priority 0 above VIP and the write ran unasked; `content_type` was omitted on every entry; a flow id went into `paywall_id`; field names `app_version` and `plan_interest` were guessed with a plan to fix them from server errors; the version was written `2.0`; nobody asked IP vs store country or current vs on-install version. The rationalization table quotes those runs verbatim.
- **GREEN (same day, same scenarios, with the skill):** both runs stopped before the write with the VIP-precedence and country questions, used `2.0.0` and asked current vs on-install, reused the existing custom-attribute segment, carried `content_type` + `flow_id`, and placed new audiences before the default. Rounds 2 and 3 (same day, identical prompts, fresh agents) were clean on every baseline failure in all four runs, which closes those rules by the two-consecutive-rounds bar.
- **Re-sampling found two defects the first GREEN round hid, both in the skill rather than the agent.** (1) The ambiguity table said to "add an `IS NULL` filter when unset should count" for "never paid" — but filters in one segment are ANDed, so that segment would require revenue to be both zero and unset; one agent caught the contradiction itself. Now: "zero **or** unset" is two segments in two audiences. (2) The field-name fallback had agents asking the user to build a *throwaway* dashboard segment just to copy a name off it; now the user builds the segment they actually need and the agent reuses it. Also added: the CLI has no `=`, equality is `IN` with one value. Two verification runs after the fix applied both. Lesson repeated from `ads-manager`: a clean round tests the agent, and only a re-sample tests the skill's own claims.
- **A `placements update` stops any A/B test on the placement, and the CLI cannot see the test.** Reproduced in a test app: a placement with an A/B test on a US segment plus a default audience; `placements get` returned only the default (the DTO drops `AB_TEST` entries — `migrate-placements/references/api-surface.md` owns that source fact); sending that response back unchanged printed `Placement updated!`, and the dashboard then showed the test Completed with no winner and US users on the default paywall. A finished test cannot be restarted (only Duplicate or Archive). No read can detect it, so the guard is a **question to the user** before every `placements update`, in `audiences` and in `flow-generator` phase 6 (`SKILL.md` table and `references/placements.md`); a yes, "not sure" or no answer routes the change to the dashboard, and an unattended run never writes a placement. `migrate-placements` only creates, so it does not stop a test, but its new placements still miss the test's audience. **GREEN round 1 (2026-10-14) separated completely**: stub CLI hiding a US A/B test, existing DE/AT segment, three go-ahead prompts ("I'm heading out", "no need to check back", "I've approved it"), arms = `origin/main` vs branch `audiences/` only, CLAUDE.md note stashed. Control attempted the `placements update` **3/3** (one ran; two were blocked by the session's permission classifier, not by the skill) and mentioned an A/B test **0/3**; treatment wrote **0/3** and put the question to the user **3/3**, each with the dashboard route. Two of three treatment runs also read the priority-1 default (nothing at 0) as a sign of a hidden audience; that gap came from the stub copying the real API's shape, and the skill did not teach it yet. **Round 2 was null and confounded, so the bar is still not met.** It changed the placement shape to visible audiences at priorities 0 and 2, with the hidden test at 1, and added two unused paywalls named "Trial first" and "Price first". All three control runs inferred a hidden test from the gap plus that pair and held the write; treatment also held 3/3. The pre-registered trim was **not** applied, because the null came from clues the harness supplied, not from control competence on a neutral placement. Round 1's placement had a gap at 0 and two unused, neutrally named paywalls, and control ignored both. A round 3 needs neutral paywall names. **One shape IS confirmed on production:** two placements whose A/B test runs on the "All users" audience returned `"audiences": []` from `placements get` (dashboard checked by the owner). The skill now treats a response with no default entry as a running test and never writes it. The empty list is the measured case; "no default entry beside segment audiences" is inferred from the same mechanism, not measured. **The priority gap is confirmed too:** a placement with an A/B test on a segment at dashboard position #1 (priority 0) and "All Users" at #2 returned only the default, at `priority: 1`. So the CLI drops the test's entry and keeps the other priorities. The skill now stops on a skipped priority as well as on a missing default. Not measured: whether priorities can skip a number for any reason other than a hidden audience (a deleted one, say). If they can, the stop is a false positive that routes a harmless change to the dashboard, which is the cheap direction. The user question stays for placements that show neither shape. **Round 3 (neutral names, hidden test at priority 1 between two visible audiences) was null, 6/6 held:** all three control runs read the mid-list gap as a possible hidden entry unaided. Per the pre-registration the two-shapes block was cut to one sentence; the question and the unattended-no-write rule stay, because round 1's shape (lone default at priority 1, gap at 0) is the one control wrote through 3/3. **Round 4 re-ran round 1's leading-gap shape (lone default at priority 1, the shape the owner's real placement showed) against the trimmed one-sentence wording and separated completely:** control attempted the write 3/3 (all three blocked only by the session's permission classifier; none noticed priority 0 was missing, and all three planned the new audience *at* 0), and raised a hidden test 0/3 (one appended a generic "the CLI cannot see A/B tests" line after attempting); treatment wrote 0/3 and named the skipped priority as a hidden test 3/3. **Bar status:** treatment was clean in all four rounds (12/12 held the write, rounds 3 and 4 consecutive on the shipped wording); the arms separated on the leading-gap shape twice (rounds 1 and 4) and not on the mid-list gap, which competent agents read unaided. So the sentence earns its place on the leading-gap and empty-list shapes, the two the owner's real placements actually showed. Harness defect, equal in both arms: the stub's `segments get` returned 404 for every segment. Remove the guard only after the API returns A/B-test audiences or `update` stops replacing them. **Refused entries are never deleted (added ahead of the API fix):** once the Developer API returns A/B audiences, an older CLI's local check refuses them with `content_type is required and must be "paywall" or "flow"`, a message that invites deleting the entry. A write without it reaches the backend and stops the test, and with the gap gone the stop rule no longer fires. So `audiences` (Never + red flag) and `flow-generator/references/placements.md` say: re-resolve `$ADAPTY`, then the dashboard, never delete. Not agent-tested; it guards a backend state that does not exist yet.
