# Maintainer notes: `migrate-placements`

Evidence and history behind the rules in `CLAUDE.md`: measurements, test rounds, dated findings. Not loaded into sessions. Read the part you need before changing a rule; add new findings here, never to `CLAUDE.md`.

## Files

- `plugin/skills/migrate-placements/SKILL.md` — the migration skill's entry point. Owns the phase spine (authenticate → read every placement, both pages and details → summarize what is migratable → ask where the flow content comes from → **create and publish one flow per distinct paywall, recording each in a `flows.json` ledger** → approve each proposed developer ID → create the flow placements → hand back the mapping and the SDK call to change) and the invariants below. Every write is a `placements create`; the skill emits no `placements update` that changes a content type, because the backend refuses it.
- `plugin/skills/migrate-placements/references/migrate.py` — the migration helpers (stdlib only, ships): audience normalization, `to_flow_audience`, the mixed-audience test, `paginate`, `group_by_paywall`, `migratable_summary`, `propose_developer_id`, `build_create_command`, and the `cli_json`/`fetch_*`/`build_plan` layer. Two traps live in code rather than in prose because prose lost to both: the `--page-size` default, and the required `content_type` on every audience entry. **`plan --flows flows.json` is how phase 7 gets its argv** — it emits a `command` per row through `build_create_command`, so the three guards (mixed-audience raise, `normalize_audience`, `to_flow_audience` carrying `segment_ids`/`priority` verbatim) sit on the documented path instead of beside it.
- `plugin/skills/migrate-placements/references/api-surface.md` — the measured-facts reference: what each `placements`/`flows` command accepts and the exact error strings the skill routes on. `SKILL.md` links into it by heading, so renaming a heading breaks the entry point silently.
- `plugin/skills/migrate-placements/references/stub-flow.json` — a minimal valid v10 config, shipped so the skill can stand a flow up with **no runtime `flowkit` dependency**. `flowkit.py` lives in `flow-generator`, which is absent from a directory-copy install of this skill alone.

## Conventions and findings: `migrate-placements`

Seven constraints carry this skill. Every one of them is a backend, CLI or dashboard fact, not a preference, so none may be softened into advice.

- **A placement's content type is immutable.** The backend refuses a change with `Placement type can not be changed.`, so the skill **creates and never converts** — no `placements update` may ever carry a different `content_type`. The consequence is the feature's whole shape: the paywall placements are left standing, which is the rollback, and every migration adds a placement rather than transforming one.
- **A developer ID is unique across every placement in the app whatever its type, and there is no delete.** So the old ID can never be reused and a bad new one is permanent. `propose_developer_id` proposes; the **user approves** every proposed ID before anything is created. Never create one from a name the agent invented and did not show.
- **A flow must be `published` before it can be attached.** A draft is refused — so the order is build → publish → place, and a create attempted on a draft is a sequencing bug, not a retryable error. **Two wordings, and the newer one replaces rather than wraps the older**: the backend sentence is `Flow must be published before placing in a placement.`, and from the CLI commit that added `src/lib/flow-help.ts` `placements create|update` match that text themselves and print `Cannot attach a draft flow to a placement — publish it first.` at **exit 2**, with the backend sentence *absent* from the output. So a check for the backend text matches on the older build and nothing on the newer one; route on `Cannot attach a draft flow` and keep the backend form as the legacy alternative. Exit 2 therefore no longer means "no request was sent" — `audienceEntryProblem` withholds a request and this one is a refused one, and only the message tells them apart.
- **Every audience entry carries an explicit `content_type`.** Without it the CLI exits **2 and sends no request**. A read from an older pod may omit the field, so a read cannot be written back unnormalized; `normalize_audience` is that shim and becomes a no-op, which is why it must accept both shapes.
- **A created flow placement is all-flow.** Mixed paywall+flow audiences are refused by the backend, and `build_create_command` raises rather than sending one — including on an all-paywall array, which is the same invariant seen from the other side.
- **`--page-size` defaults to 20 and the response carries `meta.pagination {count, page, pages}`.** Reading page 1 and reporting its length under-reports a 150-placement app by 130. `paginate` exists because prose lost to this; never replace a call to it with a single fetch. `placements list`, `flows list` and `paywalls list` are the same response shape behind the same `paginationFlags`, so all three go through one reader (`fetch_list`) and inherit the same exhaustion loop — the flow case is the one where a single page can miss precisely the row that matters.

- **Some of the migration may already be done, and phase 2 looks.** Adapty's dashboard converts a Paywall Builder paywall into a flow in one click — **Move to new builder**, documented at [convert-paywall-to-flow](https://adapty.io/docs/convert-paywall-to-flow.md) — leaving a **draft** flow that carries the paywall's layout, its copy in every locale, and its products with prices as variables. A user who has started migrating therefore already has real flows, and a run that does not look creates a **second, emptier flow for the same paywall**, permanently, because there is no `flows delete`. So `inventory` reads `flows list` and `paywalls list` by default (the paywalls for their **titles** — an audience carries `paywall_id` and no name), `plan` attaches `existing_flow_candidates` per paywall with each candidate's `status` and a `next_step` of `attach`/`publish_then_attach`, and phase 4 offers **Reuse → Convert → Build → Stub** in that order, per paywall. The stub is the **last resort**, not the fast path: it shows users a placeholder where a conversion would have shown them their own paywall.
  **The match is on the name and nothing else, because nothing else exists.** No field on a flow records the paywall it was converted from and no field on a paywall records the flow — there is no back reference in either direction — so `match_existing_flows` compares normalized titles and **proposes**; the user confirms every one. Both failure directions are real and neither is detectable: a name match can be a coincidence, and a **renamed** converted flow matches nothing, so an empty candidate list is not evidence that nothing was converted. Matching is on **tokens, not substrings** (`main` is inside `Domain expert` and is not a match). And **whether Convert is even available is unreadable** — `PaywallDTO` is `{id, product_ids, title}` with nothing about which builder made the paywall, while the button appears only on legacy Paywall Builder paywalls — so the skill describes the button and never asserts it is there.
  **The two extra reads DEGRADE rather than fail the run**, because the caller has already paid one GET per placement and an environment that cannot serve two paged lists must not cost them that: the error is recorded in `existing.error` and reported by `describe_existing`, which says the question went unanswered rather than reporting a zero. Calibrated in `tests/test-existing-flows.py` and negative-tested per mechanism (substring matching reddens 2 cases, a status-blind `next_step` 3, a single-page `flows list` 4, a non-degrading read 65 in `test-migrate-cli.py`). **One of those mutations found a test that could not fail**, which is the transferable half: the substring case used a two-token title, and normalization had already put spaces between the words, so the substring mutation passed it untouched — the hazard needs a **one-token** needle (`'main' in 'domain expert'`) to bite at all.

Two more rules about form:

- **The report is a summary, not a table of every placement.** `migratable_summary` returns counts, and `placements list` returns **no audiences at all**, so the detail pass is one `placements get` per placement — that is the split, and printing one row per placement buries the line the user has to act on.
- **The skill ships `references/stub-flow.json` specifically to avoid a runtime `flowkit` dependency.** `flowkit.py` lives in `flow-generator`, and a plain directory-copy install of `migrate-placements` alone does not have it. Never reach across skill directories for it at runtime; if the stub needs a shape it lacks, add it to the stub.
- **Two concrete ledger files, and no third.** Phase 5 writes **`flows.json`** (`paywall_id` → `flow_id`, rewritten after each flow reaches `published`) and phase 7 writes **`placements.json`** (new `developer_id` → created placement `id`, rewritten after each successful create). Both are re-read on re-entry to skip what exists, which matters because `flows create` does not deduplicate and neither a flow nor a placement can be deleted from the CLI. Never write about "the ledger" abstractly — an artifact credited with making a phase resumable and defined nowhere makes the resumability aspirational, which is exactly the defect the first review of this skill found. Only *successes* go in `placements.json`: a failure must be retried on re-entry, not skipped.
- **Phase 7's argv comes out of `plan --flows`, never out of the SKILL.md prose.** A hand-retyped `placements create` block bypasses every guard in `build_create_command` for the one irreversible command in the skill. If a future edit needs to show the argv shape, show it as *output* of the command that generates it.
